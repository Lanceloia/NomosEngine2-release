# 从 TRPG 愿望到沙盒创作工具链

Nomos 的起点是一个创作问题：**怎样让玩家在一个世界里自由尝试，并让世界依据自己的规律作出回应？**

TRPG 给了这个问题最初的形状。主持人可以理解玩家意图、安排人物与物件、推演后果，
再把实际发生的事情讲成故事。我们希望把其中的世界规则和结算建立为可维护的系统，
让作者把精力放在创造世界，让玩家的选择产生自己的经历。

随着实现推进，这个目标逐渐发展成规则驱动沙盒的创作工具链。
TRPG 是其中一种应用形态；狼人杀的身份与投票、冰宫冒险的观察与资源，
都可以用同一套声明、编译和执行机制组织起来。

这条路线由一系列具体问题推动：先制作世界，发现重复与耦合，再调整抽象，
用新的题材和反例检验调整是否有效。

## 1. 从世界模拟到可维护的世界规则

NE2 最早的 README 已提出“一套 YAML 与配置定义可演化世界”，
用属性图保存实体与关系，通过泛型操作和规则推进变化。
多个 world-pack 帮助我们尝试把相同机制用于不同世界。

实现中的难点逐渐明确：规则、宿主流程、玩家呈现和状态修改之间，
需要比“放在不同文件夹”更准确的职责边界。一次观察怎样成为角色的知识？
一个物件怎样拥有自己的状态？多人参与的行动怎样共同结算？

GV（Greybell Vigil）与 FG（Frontier Guild）把这些问题带进具体场景。
世界中的交付、阅读、发言和听见分别有实际发生；角色的局部信息又会影响后续选择。
这些试验推动项目把实体状态、行动与事件、局部读回和来源记录分开建模。

**重构所得：** K0 逐步承担通用的状态权威、准入、因果结算与原子发布；
题材规则在其上组织。世界案例同时成为发现基础能力缺口的方法。

## 2. 从接好一个世界到让作者写出世界

当世界越来越丰富，维护 Python 接线开始成为创作负担。
这促使我们把问题改写为：**作者应该声明什么，编译器应该替作者完成什么？**

一个关键区分是：

- **Source：** 声明实体、能力、世界规则、可见性与控制方式。
- **行动见证：** 给出某个控制者希望尝试的行动序列与检查目标。

前者建立可玩世界，后者帮助工具验证一段经历。
实际故事来自运行时的选择与规则结算。

2026-09-28，GV 的 R1 到岗察觉规则成为早期 LawDef → C0 → K0 消费者：
规则定义与具体绑定分开，改变条件会改变真实察觉链。
它给出了作者规则驱动执行的第一条纵向证据，随后推动 Action、Event、时间和开局组合继续进入编译链。

**重构所得：** 规则定义、绑定与数据资产分工；C0 把作者声明转成可执行规则，
T0 使用同一产物运行行动见证。

## 3. 狼人杀让“通用”变得可以检验

狼人杀提供了紧凑而有区分度的编译器试验场。
人数、身份分布、职业能力和投票规则的变化，会同时影响实例、选项和真实后果。

2026-09-30，三人作者世界进入实际运行；其后逐步扩展参与者与职业规则，
作者文件转向更易阅读的 YAML。今天的演示保留三类编辑实验：

- 加入禁止自救条件，改变同一请求的准入结果。
- 把共同袭击从全票一致换为多数票，改变实际死亡结果。
- 换女巫、增加参与者，改变本地视图、选项和行动来源。

这些实验形成了一个可操作的判断标准：
**编辑作者声明，实际运行的实例、来源或后态也应随之变化。**

**重构所得：** 实例域、规则复用、角色授予与开局分离得到真实消费者校准。
见[实验导览](PROJECT_TOUR.md)和[证据地图](SHOWCASE_MATRIX.md)。

## 4. M1 把作者负担和运行成本暴露出来

M1 冰宫冒险把位置、资源、检定、寒冷、观察、人物行动和营救组合到同一世界。
随着组合规模增长，作者文件出现了重复接线和长表达式，运行时也出现了重复读取与验证。

因此，优化开始同时沿两个方向推进：

| 作者侧 | 编译与运行侧 |
| --- | --- |
| 用具名类型表达领域含义 | 编译时完成类型与精确权限检查 |
| 用语义谓词表达存在、唯一和有限查询 | 保留谓词结构，使用专用短路求值 |
| 用模块组织区域与共享规则 | 从受检 IR 形成唯一执行绑定 |
| 让输出目的地集中声明 | 编译器展开可机械推导的接线 |
| 复用规则定义和参与者声明 | 用封存布局生成执行计划，运行时核对当前状态 |

2026-10-03 起，Action 与 due 规则保留受检语义 IR；随后统一 Program 绑定。
2026-10-04，原独立 ontology/lowering 包中的活跃类型与绑定能力归入 C0，
使作者语义检查与执行后端拥有更清楚的组织边界。

**重构所得：** IR 成为作者表达与后端执行之间的桥梁。
Lib 存放可复用定义，Source 选择与装配世界，编译器处理类型、权限和执行组织。
实现与例子见[代码地图](CODE_MAP.md)、[执行后端](EXECUTION_BACKEND.md)。

## 5. 从探索原型到可维护的发行基线

M1 的运行推动了调度、状态隔离、表达式执行和字段校验的优化。
随后整理发行基线时，核心审计又用反例检查了开局隔离、事务重入和精确写权限。

例如：两个参与者使用相同状态类型，也需要分别声明写权限；
一次开局检查持有的临时值，需要与权威状态隔离。
这些具体反例帮助合同与实现重新对齐。

发行整理将核心实现、作者资源、安装入口和维护文档组织到独立仓库。
新的核心随后同步回研究仓库，M1 Web 通过明确依赖消费发行运行时。

**重构所得：** 研究历史与使用入口分别组织；核心、作者工具和应用各有维护边界。
工程取舍及对应短测试见[设计说明](DESIGN.md)。

## 为什么形成当前 C0 / K0 / T0

今天的分工来自上述问题的收敛：

```text
作者定义：Lib / Ports / Source
                   │
           C0 检查、编译与绑定
                   │
                Program
                   │
开局 Assets ──── Start
                   │
               K0 Session
                   │
     行动提议 → 准入与结算 → 状态、发生来源、本地读回
                   │
           终端 / M1 Web / 其他控制者

T0：对同一 Program 和 Assets 实际执行行动见证，检查目标。
```

- **C0** 面向作者：把声明、类型、规则与权限组织为可执行世界。
- **K0** 面向结算：维护权威状态、发生来源和一次行动的事务边界。
- **T0** 面向验证：运行具体行动见证，使创作意图可以接受实际检验。
- **应用与未来的 LLM DM** 面向交互和创作：读取授权信息、提出行动、讲述实际经历。

当前通过狼人杀和 M1 校准这些分工。
长期方向是让可复用规则、库与工具共同支撑更多沙盒世界，
涵盖 TRPG 冒险、桌游流程，以及其他规则驱动的交互内容。

# 发起者的工作与工程证据

NomosEngine2 的发起者是梁宇方。后期主要代码由 Codex 与协作者实现、审阅，
发起者持续负责目标、语义决策、反例、方向调整与亲自验收。

## 一个决定怎样成为当前系统

最关键的追问是：“作者应该声明能力，还是写一串必须发生的剧情步骤？”
发起者要求将两者分开：作者源码建立世界允许的行动空间，剧情是运行时实际发生的历史；
期望的行动序列可以作为工具检查源码的见证，不应成为运行时的剧本。

### 案例：从预期剧情到可编辑世界

**发现问题。** GV 通信、察觉与阅读可以依靠专用流程接成一条预期经历，
但作者修改规则后，流程是否仍在替世界决定结果，变得难以核对。

**比较方案。** 一种方案把预期行动序列作为源码中的流程；另一种方案让源码声明允许发生什么，
把预期序列单独交给验证工具。发起者选择后者：同一个世界能容纳不同选择，
规则修改的效果也能沿相同行动序列对照。

**工程落点。** C0 编译规则，开局数据绑定到 Program；交互与 T0 见证检查使用相同的
K0 准入和发布路径。T0 报告指定路线在哪一步停止，以及目标是否达成。

**创作动机。** 发起者希望作者可以先写精彩故事，再探索支持它的世界事实、能力与规则。
T0 的长期设计由此包含故事约束提取、规则候选设计和实际见证检查；当前完成的是见证检查。
故事引导创作，实际游玩仍保留玩家选择。这也解释了为何世界源码与预期剧情需要分别组织。

**反例与验收。** 发起者亲自只修改女巫规则中的禁自救条件，保留开局和行动见证。
前九步的十二条实际发生及来源相同，第十步从发布变为拒绝；换职业、扩人数则改变选项、
本地视图和实际来源。对应[复现实验](PROJECT_TOUR.md#先看三个实验)和
[演进记录](PROJECT_EVOLUTION.md#2-从接好一个世界到让作者写出世界)可以继续追问。

人类负责问题提出、方案选择、语义裁决和上述亲测；AI 协作者承担后期编译器、
内核接线、验证工具的代码实现与技术检查。

这个决定形成了当前三条可检查路径：

| 责任 | 代码／实验 |
| --- | --- |
| C0 编译规则与世界声明，开局数据单独 Start | [Program 阶段测试](../tests/nomos_c0/test_program_phases_v1.py)、[世界前端](../src/nomos_c0/graph_frontend_v1.py) |
| K0 对真正提交的行动重核当前态并原子结算 | [行动准入](../src/nomos_c0/composable_action_v1.py)、[原子会话](../engine/kernel/src/nomos_kernel/_atomic_inmemory_session.py) |
| T0 使用同一产物实际执行有限见证 | [见证执行](../src/nomos_t0/witness_v0.py)、[规则编辑实验](../tools/release_rule_edit_demo.py) |

发起者亲自按 README 修改禁自救条件、换女巫和扩人数，再撤回临时改动。
验收检查了前九步来源一致、第十步由成功变为拒绝，以及职业、选项、私有视图和真实来源的联动。
对应复现入口见[规则编辑](SHOWCASE.md)和[人物实验](showcase/world-edits/README.md)。
发起者提出了问题、裁定了语义并验收结果；这些路径的后期 Python 实现归于 AI 协作者。
上面的代码与实验可核对系统结果，演进过程见[项目历史](PROJECT_EVOLUTION.md)。

## 可现场讨论的问题

1. 为什么 Source 与见证要分开？如果把见证当成运行脚本，会怎样限制规则编辑？
2. 候选存在、当前态准入失败和准入后结算缺陷，各在什么位置处理？
3. 从课程代码选一段本人实现，解释数据结构、一次正常运行及一个失败分支。

这些入口用于继续核查与交流，系统规模和 AI 产出行数不作为个人手写能力的度量。

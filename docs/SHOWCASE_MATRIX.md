# 用一组实验解释 NomosEngine2

我们要回答的不是「能不能挡住一个请求」，而是：**作者能否声明一个世界，让人物的
选择在共同规则下产生可追溯的故事，并通过修改声明真正改变这个世界？**

这需要不同实验共同支撑。一次条件判断不能证明通用世界建模；一条营救路线也不能
证明任意沙盒剧情都可生成。本页是展示规划与证据索引，不是新能力的实施授权。

核对日期 2026-10-10。E1–E4 已用谓词与类型别名整理后的 `960435fe3` 重新采集；
三份逐步报告与旧版结构化内容相同。新证据独立保存，旧报告、摘要与画面保持原字节。

## 三条展示线

| 展示线 | 陌生读者应该理解什么 | 优先材料 |
| --- | --- | --- |
| 编辑世界 | 人数、职业和能力归属来自作者声明，而不是为固定几个人写死的程序 | 狼人杀扩人数、换女巫 |
| 编辑规则 | 相同人物、开局和行动，在不同规则下产生不同的真实判定或后态 | 禁止自救、共同袭击规则替换 |
| 规则共同产生故事 | 位置、资源、局部知识和人物选择互相作用，结局不是宿主指定的分支 | M1 的永焰、寒冷、观察与营救 |

三条线共用现行 C0/K0 编译与执行链；不用三个单独写死结果的演示来凑数量。
源码差异和真实记录负责证明，动画只解释变化，不能增加证据没有支持的结果。

### E3／E4：编辑规则

E3 的[报告](showcase/self-heal-predicates-v1/result.json)与[采集摘要](showcase/self-heal-predicates-v1/manifest.json)支持共同前缀和准入分叉。
实验工具只在内存修改规则，两版分别 Compile／Start／Run，不是运行时热替换。
成功目标是使用解药，不是赢得游戏；拒绝发生在准入，不是已发布行动又被撤销。

E4 的[中文实验页](showcase/wolf-vote/README.md)、[逐步报告](showcase/wolf-vote/evidence-predicates-v1/result.json)
与[采集摘要](showcase/wolf-vote/evidence-predicates-v1/manifest.json)将上述具名模块的
`test_source_selects_unanimity_or_majority_without_changing_the_opening`
所验证的组合整理成可复现对照。同样的狼人投票为 F、F、E，仅把选中的 Law 引用换为
`event.select_majority`。两版各发布十项 Action、十三条发生记录，最终都进入第二轮白天且
尚无胜方；前者无人死亡，后者 F 死亡。差异体现在世界后态，不要求发生数量一定不同。
报告保存七个 owner 的逐步状态及发生来源，仅供作者审计，不把私有职业交给玩家。

### E5／E6／E7：规则共同产生故事

使用安装包内同一套 [M1 装配清单](../src/nomos_examples/everflame/world.bundle.yaml)：
[局部观察](../src/nomos_examples/everflame/source/rules/local_observation.yaml)、
[解冻](../src/nomos_examples/everflame/source/rules/thaw.yaml)、
[寒冷](../src/nomos_examples/everflame/source/rules/cold.yaml)、
[本地选项和读回](../src/nomos_examples/everflame/source/control/seats.yaml)、
[有限 NPC 策略](../src/nomos_examples/everflame/source/control/policies.yaml)。

已有整局记录见[发行收束](RELEASE_BASELINE_CLOSURE.md)：43 项玩家行动、1180 条发生，
居民实际到达外岸、仪式中断。它是同路线的正确性／性能核对，不是两个剧情结局的
对照，也没有证明所有 NPC 或规则组合正确。本轮核对其外部原始报告摘要与文档一致，
报告没有新增、覆盖或重跑；该文件尚未随展示仓库分发。

展示优先截取可读的短链：真实位置／充能变化 → 已授权保护读回 → 下一次寒冷结算；
或观察 → 获得有限证据 → 出现目标 → 提交解冻 → 扣资源并改变目标状态。
保护会即时重新推导，不应画成寒冷损伤连续发生；同种子也不能保证两条分歧路线永远
使用同一骰序，需核对实际取骰与来源。解冻、邀请、到达安全区是不同事实，不合成
一个未经验证的「全部救出」图标。

## 选项联动是待研究缺口

目前 E3 的菜单条件在 Source `offers.when`，最终准入在 Lib `guard.require`。
新增禁自救条件只改后者，因此候选仍存在。K0 的当前态复核必须保留，但公开规则
应该怎样影响正常选项，不能仅由「内核反正会拒绝」来回答。

需要分别研究：能力是否授予、本人可知的行动条件、世界权威当前态准入。
不能把全部 guard 直接搬到菜单：其中可能包含人物不知道的限制，选项消失本身也
可能泄漏信息。公开限制应怎样复用于可用性，以及未知限制下是否有真实的尝试行动，
须明确语义后实现；不先复制一份条件，不先改标签假装已闭合，也不承诺编译器已能
自动解决它。新生实体、所有权与跨 Actor 知识边界仍按现行合同升级裁决。

## 建议制作顺序

1. E1／E2／E4 已保存；先由读者核对这些编辑差异与真实结果，不继续雕琢旧 GIF。
2. 明确公开限制／局部知识／准入的关系，再选择真正能说明选项联动的实验。
3. 从 M1 已有机制选一条短因果链，保存必要本地视图与实际事件，不为展示跑整局性能。
4. 把三条线编排成首页实验地图；主画面呈现世界和人物，源码与来源按需展开。
5. 最后才为确有解释收益的变化制作短动画。缺证据的部分不靠画面补足。

这是建议顺序，不自动启动核心开发、资产改写、Web 切换或新测量。

E1／E2／E4 均使用具名短测试与真实采集，不以动画或测试夹具替代世界运行。
历史禁自救报告与发行整局外部报告保持原记录；新短对照独立采集，不覆盖旧证据。
